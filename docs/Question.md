# 仕様確認事項

実装を進める中で `docs/REQUIREMENTS.md` 等だけでは判断がつかなかった仕様上の疑問と、
判断がつくまで採用した暫定方針をここに記録する。問題ないか確認してほしい。

## FR-06 リサイズ: 「縦結合の初期値は幅揃え、横結合の初期値は高さ揃え」の解釈

- 該当箇所: `docs/REQUIREMENTS.md` FR-06「縦結合の初期値は幅揃え、横結合の初期値は高さ揃えとする。」
- 疑問: これは (a) アプリ起動時の `EditorState` の初期値としてのみ適用されるのか、(b) 結合方向(縦/横)を切り替えるたびに毎回サイズモードを対応するfit系に自動でリセットする仕様なのか、判断がつかなかった。(b)の場合、ユーザーが手動で選んだサイズモード(例:カスタム)が方向切替のたびに上書きされてしまう、という別のUX上のトレードオフも生じる。
- 暫定方針(今回採用): どちらも実装せず、`sizeMode` の初期値は既存どおり `"original"`(P0-02で定義済み)のままとし、結合方向の切り替え(`settings/direction`)でも `sizeMode` は変更しない。ユーザーが「原寸/幅揃え/高さ揃え/カスタム」を明示的に選ぶ形にした。
- 理由: (b)の自動リセット実装は、良くも悪くも既存のテスト資産(異なる幅/高さの画像を使う複数のテストケース)に影響する変更範囲が大きく、かつユーザーの手動選択を意図せず上書きするリスクがあるため、確認なしに実装するのは避けた。
- 確認したいこと: FR-06のこの一文は「アプリ初回起動時のデフォルト値」の意味で良いか、それとも「方向を切り替えるたびに追従してほしい」という意味か。後者であれば、ユーザーが直前に手動でサイズモードを変更していた場合の扱い(上書きする/しない)も合わせて教えてほしい。

## FR-06 リサイズ: 「幅揃え」「高さ揃え」の基準サイズ

- 該当箇所: 同じくFR-06。「幅揃え」「高さ揃え」は、揃える先の基準サイズ(どの画像の幅/高さに合わせるか)が明記されていない。
- 暫定方針(今回採用): 一覧の**最初の画像**(並び替え後の先頭)の幅(幅揃えの場合)・高さ(高さ揃えの場合)を基準とし、他の画像を縦横比を保ったままそれに合わせて拡大・縮小する。実装: `src/app/page.tsx` の `applySizeMode`。
- 理由: 複数の基準候補(最初の画像/最も広い画像/最も狭い画像など)の中で、決定的かつ単純な挙動として「先頭画像」を採用した。スクリーンショット結合という用途上、連続キャプチャした画像は幅がほぼ揃っていることが多く、実用上は基準の選び方による差が出にくいと考えている。
- 確認したいこと: 「最初の画像基準」で問題ないか、それとも別の基準(最大幅/最小幅など)を意図しているか。

## FR-06 リサイズ: 「カスタム」モードで指定するのは幅か高さか

- 該当箇所: 同じくFR-06。「指定サイズ」(カスタムモード)の数値が幅・高さどちらを指すのか明記されていない。
- 暫定方針(今回採用): 結合方向に応じて対象軸を切り替える。縦結合中は入力値を「幅」として扱い(`fitToWidth`)、横結合中は「高さ」として扱う(`fitToHeight`)。UIのラベルは軸を明示せず「カスタムサイズ(px)」とした。
- 理由: 縦結合では画像の左右端を揃えたい(=幅を揃えたい)、横結合では上下端を揃えたい(=高さを揃えたい)というのが最も自然な意図だと考え、「幅揃え/高さ揃え」の軸選択ロジックと一貫させた。
- 確認したいこと: この解釈で問題ないか。あるいは、モードに関わらず常に「幅」を指定する数値にすべきか。

## P4-04 暗号化ZIPの検出方法(実装方針の確認、ブロッキングではない)

- 該当箇所: `docs/IMPLEMENTATION_PLAN.md` P4-04「暗号化、入れ子、破損、非対応アーカイブを拒否する」。
- 検討: `fflate`(導入済みライブラリ)の公開APIは、ZIPローカルファイルヘッダーの暗号化フラグ(汎用目的ビットフラグのbit 0)を直接は公開していない。正確に「暗号化されている」ことだけを事前判定するには、ZIP形式のセントラルディレクトリを自前でバイナリパースする必要があり、実装・テストのコストが大きい。
- 採用した方針: 暗号化・破損・非対応圧縮方式を**個別に事前検出せず**、`fflate`の展開処理(Worker内)を実際に実行し、例外が発生した場合はまとめて「アーカイブを展開できませんでした」という単一のエラーとして安全に拒否する。入れ子ZIP(ZIP内に`.zip`ファイルが含まれる)だけは、ファイル名の拡張子で事前検出できるため`src/lib/validation.ts`の`isNestedArchiveEntry`で個別に判定している。
- 理由: `docs/CLAUDE.md`のガードレール「ZIP extraction runs in a Web Worker; validate signatures and enforce size/count limits」が求めているのはメインスレッドがフリーズしないことと上限の強制であり、暗号化かどうかを正確に分類することそのものではないと判断した。展開に失敗するアーカイブ(暗号化・破損・非対応形式のいずれであっても)を一律に安全側で拒否すれば、この目的は満たせる。
- 確認したいこと: この一律拒否の方針で問題ないか、それとも暗号化されたZIPだけは他の失敗(破損など)と異なる文言のエラーメッセージを出すべきか。
- **追記(Codexレビュー1回目後の検証結果)**: 外部レビュー(Codex CLI)で「`fflate`の`unzipSync`はCRC-32を検証せず、暗号化フラグも無視する」という指摘を受け、Node上で実際に(a) 1バイトだけ壊れた(サイズは不変の)エントリ、(b) 暗号化フラグを立てたが実データはそのままのエントリ、をそれぞれ`unzipSync`に通して検証した。結果、両方とも例外を投げずに(壊れた/フラグの立った)データがそのまま返ってきた。**つまり「展開が例外を投げることをもって破損・暗号化の検出とする」という前提は成立しない。**
  - 上記の理由により、ZIP形式のバイナリを自前でパースして暗号化フラグを検出する実装は今回も追加しなかった(引き続き検証待ちの暫定方針のまま)。ただし「展開が失敗する」という前提は誤りだったため、コメント上の説明を修正した。ユーザーが望むなら、ZIPのセントラルディレクトリを直接パースして暗号化フラグ・CRCを検証する実装を追加することもできる。
- **追記(Codexレビュー2回目: サイズ上限迂回について、1回目の追記の誤りを訂正)**: 1回目の追記で「展開後サイズを偽装してもfflateはその偽装値でバッファを確保し実データを切り詰める」と書いたが、これは**DEFLATE方式のみに当てはまり、STORE(無圧縮)方式には当てはまらない**という指摘を受け、実際に検証して確認した。STORE方式では`compressedSize`(圧縮サイズ)が実データのサイズそのものであり、宣言された`uncompressedSize`(展開後サイズ)フィールドを偽装しても、fflateは`compressedSize`分の実データをそのまま返す(31MBの実データに対し展開後サイズを1バイトと偽装しても、実際に31MBがそのまま返ってくることをNode上で確認した)。これは`uncompressedSize`だけを見て上限判定していた実装の**実際のバイパス経路**であり、単なる理論上の懸念ではなかった。**修正済み**: `validateZipEntries`(`src/lib/validation.ts`)は、`compressedSize`と`uncompressedSize`の大きい方(`effectiveSize`)を実際に確保されうるサイズとみなして1件あたり・合計の上限判定を行うようにした。STORE方式ならcompressedSizeが、DEFLATE方式ならuncompressedSize(fflateが実際に切り詰める値)が、それぞれ正しく効く。
- **追記(Codexレビュー2回目: 破損データの整合性について)**: 「先頭バイトの署名検証は形式判別であり、ファイル全体の整合性検証ではない」という指摘は正しい。実際の安全網は署名検証**単独**ではなく、署名検証と、その後の`createImageBitmap()`によるデコード失敗時のハンドリング(`Promise.allSettled`、Phase 1のP1-03から存在)の**組み合わせ**である。ファイルの先頭バイトだけがたまたま有効なPNG/JPEGヘッダーと一致し、中身が壊れているデータは、署名検証は通過しても`createImageBitmap()`のデコード自体が失敗する可能性が高く、既存の失敗ハンドリング経路(壊れた画像として一覧から除外し、ユーザーに通知する)でカバーされる。ただし、これは「ブラウザのデコーダが壊れたデータを確実に検出する」という前提に依存しており、CRC-32のような数学的に確実な整合性検証ではない。暗号化・破損アーカイブの拒否を要求仕様どおり確実にしたい場合は、ZIPのセントラルディレクトリを自前でパースしてCRC-32を検証する実装が必要であり、現時点では未実装(ユーザーの要望があれば追加できる)。
